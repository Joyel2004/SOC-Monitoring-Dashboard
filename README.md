# SOC Monitoring Dashboard

## Overview

This project extends my Wazuh SIEM home lab by adding additional network visibility and security data visualisation using NetAlertX and Grafana.

Wazuh provides the underlying security telemetry and alert data, while Grafana is used to create a customised SOC monitoring dashboard. NetAlertX provides additional visibility into devices connected to the local lab network.

The project demonstrates how multiple monitoring tools can be combined to provide a more centralised view of security activity within a home SOC environment.

## Project Objectives

- Integrate Wazuh security alert data with Grafana.
- Build a customised SOC monitoring dashboard.
- Visualise security alert trends and severity levels.
- Monitor failed authentication events.
- Monitor File Integrity Monitoring (FIM) activity.
- Identify high-severity security alerts.
- Deploy NetAlertX for local network device monitoring.
- Gain practical experience integrating multiple security monitoring technologies.

## Lab Architecture

The monitoring environment consists of:

- **Windows 11 Endpoint** - Generates security telemetry and runs the Wazuh agent.
- **Ubuntu SOC Server** - Hosts Wazuh components and NetAlertX.
- **Wazuh Indexer** - Stores indexed Wazuh security alert data.
- **Grafana** - Queries Wazuh alert data and presents customised SOC visualisations.
- **NetAlertX** - Provides visibility into devices present on the local network.
- **Docker** - Provides the containerised environment used to run NetAlertX.

### Security Monitoring Flow

Windows Endpoint → Wazuh Agent → Wazuh Manager → Wazuh Indexer → Grafana Dashboard

Local Network → NetAlertX → Network Device Visibility

NetAlertX was deployed in a Docker container on the Ubuntu SOC server to provide additional visibility into devices connected to the local network.

The deployment used persistent storage for NetAlertX data and host networking to support local network device discovery.

The NetAlertX interface provided visibility into discovered devices, their connectivity status, and network presence.

## Grafana and Wazuh Integration

Grafana was configured to query security alert data stored within the Wazuh Indexer.

The Wazuh alert index was added as a Grafana data source, allowing security events generated by Wazuh to be queried and transformed into custom visualisations.

The `timestamp` field was used as the time field for Wazuh alert data.

### SOC Dashboard

A custom Grafana dashboard was created to provide a central view of security activity collected by Wazuh.

The dashboard includes:

- **Total Wazuh Alerts** - Displays the overall number of alerts within the selected time range.
- **Wazuh Alerts Over Time** - Visualises changes in alert volume over time.
- **Failed Login Alerts** - Tracks Windows authentication failures.
- **FIM Alerts** - Displays File Integrity Monitoring activity.
- **High Severity Alerts** - Monitors Wazuh alerts with rule levels between 10 and 15.
- **Alerts by Severity Level** - Groups alerts by Wazuh rule level to show the distribution of alert severity.

## Security Monitoring Results

The completed dashboard successfully visualised security telemetry collected from the Windows endpoint through Wazuh.

During the selected 30-day monitoring period, the dashboard displayed thousands of Wazuh alerts across several severity levels. The majority of observed alerts were lower-to-medium severity events, while no alerts within the configured high-severity range (Wazuh rule levels 10-15) were present during the selected period.

### Failed Authentication Detection

Failed Windows authentication attempts were successfully detected by Wazuh and displayed within the Grafana dashboard.

This demonstrates the monitoring pipeline from Windows security events through the Wazuh agent and manager to the Wazuh Indexer, where the events could then be queried and visualised using Grafana.

### File Integrity Monitoring

Wazuh File Integrity Monitoring (FIM) generated alerts when monitored files and registry objects changed on the Windows endpoint.

Test activity included creating, modifying, and deleting a monitored file. Wazuh detected these changes and generated corresponding security events.

The dashboard also showed a significant volume of FIM activity generated by normal Windows file and registry changes, demonstrating why SOC analysts must distinguish expected system activity from potentially suspicious modifications.

### Alert Severity Analysis

Wazuh rule levels were used to categorise the severity of detected events.

The Grafana severity visualisation grouped alerts by `rule.level`, making it possible to quickly identify the distribution of alert severity and investigate higher-priority events.

A separate high-severity panel filtered for Wazuh rule levels 10-15. No events within this range were observed during the selected monitoring period, which demonstrates that the dashboard correctly represents the absence of matching alerts rather than artificially generating security incidents.

## Security and Hardening

Security controls were applied to the Ubuntu SOC server to reduce unnecessary network exposure and restrict access to services used by the monitoring environment.

### UFW Firewall

Ubuntu's Uncomplicated Firewall (UFW) was configured using a default-deny approach for inbound connections.

Only ports required by the lab services were permitted, with access restricted to the Windows monitoring host where appropriate.

Key services included:

| Port | Protocol | Purpose |
|---|---|---|
| 1514 | TCP | Wazuh agent event communication |
| 1515 | TCP | Wazuh agent enrollment |
| 443 | HTTPS | Wazuh Dashboard access |
| 9200 | TCP | Wazuh Indexer access used by Grafana |
| 20211 | TCP | NetAlertX web interface |
| 20212 | TCP | NetAlertX API |
| 8010 | TCP | Reserved for the alert enrichment API |

This configuration follows the principle of least privilege by exposing only the network services required by the monitoring environment.

### NetAlertX Container Hardening

NetAlertX was deployed using Docker rather than installing the application directly on the Ubuntu host.

The container configuration included several security and reliability controls:

- A read-only container filesystem was used where possible.
- Linux capabilities were dropped and only the capabilities required by NetAlertX were explicitly enabled.
- Persistent application data was stored separately on the Ubuntu host.
- File permissions were restricted for the NetAlertX data directory.
- Temporary storage was provided separately using `tmpfs`.
- Host networking was used because NetAlertX requires local network visibility for device discovery.

These controls reduced unnecessary container privileges while maintaining the functionality required for network discovery.

### Network Segmentation and Access Control

The Ubuntu virtual machine used VirtualBox bridged networking, allowing it to operate as a separate device on the local network.

This provided direct communication between the Windows endpoint and Ubuntu SOC server while allowing firewall rules to control which services could be reached.

Access to monitoring services was restricted rather than exposing every service on the Ubuntu system.

## Challenges and Troubleshooting

Several technical issues were encountered while building the monitoring environment. Resolving these problems provided practical experience with Linux administration, networking, Docker, and security monitoring tools.

### Duplicate IP Address Conflict

During the lab, the Ubuntu SOC server was configured with a static IPv4 address. After a system restart, the Windows host received the same address through DHCP, creating an IP address conflict.

Connectivity tests initially appeared unusual because the Windows system was effectively communicating with its own assigned address rather than the Ubuntu server.

The issue demonstrated the difference between manually assigning a static IP address and reserving an address within the router's DHCP configuration.

This reinforced the importance of IP address management when deploying servers that require predictable network addresses.

### NetAlertX Container Startup Failure

The initial NetAlertX Docker configuration failed its startup security checks.

Container logs were examined to identify problems relating to Linux capabilities, filesystem permissions, networking, and container security requirements.

The Docker configuration was adjusted to use the permissions and capabilities required by NetAlertX while removing unnecessary privileges. Persistent storage and temporary filesystem configuration were also configured appropriately.

After correcting the configuration, the container started successfully and NetAlertX became accessible from the Windows host.

### NetAlertX Network Binding

NetAlertX initially experienced problems binding its web service to a specific Ubuntu IP address when the VM's network address changed.

The service configuration was changed to listen on `0.0.0.0`, allowing the service to bind to the Ubuntu network interfaces while UFW continued to control which systems could access the service.

This demonstrated the difference between an application's listening address and firewall-based network access control.

### Grafana Time Field Configuration

When configuring the Wazuh Indexer as a Grafana data source, the correct Wazuh time field had to be identified.

Wazuh alert documents use the `timestamp` field for event time. Configuring Grafana to use this field allowed alert data to be queried correctly across selected time ranges.

This was important when creating time-series visualisations of Wazuh alerts.

### Grafana Stat Panel Aggregation

During dashboard development, some Grafana Stat panels initially displayed unexpected values.

The queries returned alert counts grouped into time buckets. Using the `Last` calculation displayed only the value from the final time bucket rather than the total number of alerts across the selected period.

Changing the Stat calculation to `Total` allowed the dashboard to display the complete alert count for the selected time range.

This demonstrated the importance of understanding both the underlying query and the visualisation aggregation when analysing security data.

### Time Range During Alert Investigation

Some previously generated security events initially appeared to be missing from the Grafana dashboard.

The dashboard was configured with a relatively short time range, while the test events had been generated several days earlier. Expanding the dashboard to the last 30 days made the historical events visible.

This reinforced an important SOC investigation principle: the selected investigation time window can directly affect whether relevant security events are visible.

## What I Learned

This project expanded my understanding of how security monitoring data can be collected, stored, queried, and presented across multiple tools within a SOC environment.

Integrating Grafana with the Wazuh Indexer helped me understand the difference between generating security alerts and presenting those alerts in a format that allows an analyst to quickly identify trends and areas requiring investigation.

Building the dashboard also demonstrated the importance of understanding the underlying data. Selecting the correct time field, query filters, aggregation methods, and dashboard time range directly affected the accuracy of the information presented.

Deploying NetAlertX provided additional experience with network visibility and Docker. Troubleshooting the container configuration reinforced the importance of examining application logs, understanding service permissions, and granting only the capabilities required by an application.

The networking issues encountered during the project also improved my understanding of DHCP, static addressing, service binding, firewall rules, and communication between virtual and physical systems.

Overall, the project demonstrated that effective security monitoring involves more than installing tools. The monitoring pipeline must be configured, tested, validated, and understood so that the information presented to an analyst is meaningful.
